# Release Guard · выпуск «Книги сказок»

## Команды владельца

**Публикуй из ChatGPT:** по явной команде владельца агент объединяет проверенный PR в `main`, используя заголовок merge-коммита `Публикуй: <версия>` и проверку точного SHA головы PR. Успешный первый прогон Quality checks для этого коммита автоматически запускает Release Guard. Выпуск допускается только для события push в `main` этого репозитория, инициированного владельцем, с неизменным SHA и указанным заголовком. Обычные изменения, PR из других веток, повторные прогоны и неуспешный CI не запускают публикацию. Проверка архива, контроль рабочего сайта и совместимый откат остаются обязательными. Ручной запуск и скрипт ниже остаются альтернативой при недоступности автоматического пути; не запускай их одновременно с автоматическим выпуском.

Владелец даёт агенту одну команду. Агент использует действующее подключение GitHub под `rusai-dev` и выбирает открытый PR кандидата. Готовность PR сама по себе не разрешает публикацию. Команды для агента в рабочей копии:

```sh
node tools/release-owner.cjs Публикуй 184
node tools/release-owner.cjs Проверь
node tools/release-owner.cjs Проверь 184
node tools/release-owner.cjs Восстанови
```

**Публикуй** дожидается уже запущенного CI для головы PR, проверяет актуальный `main`, объединяет PR с защитой по SHA и дожидается автоматически запущенных 21 проверки нового SHA. Затем ожидает автоматически запущенный Release Guard (не создаёт второй запуск). Для старых merge-коммитов без явного заголовка сохраняется ручной путь. **Проверь** сверяет рабочий сайт или архив выбранного PR. **Восстанови** использует совместимый архив из успешной проверки опубликованного SHA. Если живой SHA сменился, архив истёк или совместимость не подтверждена, восстановление блокируется. Среда `github-pages` допускает только `main`, а запись доступна только команде владельца. Ручной запуск через GitHub Actions доступен из `main` после слияния.

Регламент подготовки нового релиза. Измени версию в `release.json`, затем запусти `node tools/shell-integrity.cjs --sync-version`. Она выводит согласованные версии в UI, URL оболочки и Service Worker. Для проверки используй `node tools/shell-integrity.cjs --check`. Слияние корректной ветки при источнике Pages **GitHub Actions** запускает подготовку, а опубликованный сайт сохраняет действующий релиз до команды владельца.

## Как проходит выпуск

1. **ПОДГОТОВКА**. Quality checks берёт точный SHA и создаёт архивы приложения и последнего работающего релиза. SHA-256 учитывает каждый файл архива. Два последних выпуска до подключения Release Guard, 1.5.208 и 1.5.209, связываются с опубликованными коммитами по HTML, версии, Worker и обязательным ресурсам. Последующие версии публикуют `release-proof.json` с SHA и идентификатором сборки.
2. **ПРОВЕРКА**. Node, полные сценарии Chromium и WebKit, снимки обоих движков и точный переход с работающей версии. Браузерные сценарии разнесены на независимые задачи, каждый проход сохраняет время выполнения. Устаревшие прогоны отменяются. Длительность ограничена, процессы браузера закрываются через Playwright и общий тайм-аут.
3. **ГОТОВО К ПУБЛИКАЦИИ**. Обязательные задачи успешны для последнего прогона того же SHA. Истёкший архив, изменившийся `main`, другой опубликованный SHA и отсутствующий результат дают **ЗАБЛОКИРОВАНО**. Для рабочего выпуска используются прогоны `main`, для проверки черновика доступен успешный прогон PR того же репозитория или явный прогон ветки. Приёмка на физическом iPad и состояние независимой копии работ фиксируются отдельно.
4. **ПУБЛИКАЦИЯ**. В GitHub Pages передаются неизменённые байты проверенного архива из Quality checks. Контроль перед этим повторно сверяет текущий сайт и SHA. Процесс публикации сериализован.
5. **ОПУБЛИКОВАНО НА СЕРВЕРЕ**. Сайт отдал ожидаемые HTML, манифест, Worker и ресурсы, а браузер прошёл основные маршруты без критических JavaScript-ошибок. Длительность внешнего развёртывания GitHub измеряется отдельно. Обновление устройства в этот момент ожидает подтверждения.
6. **ВОССТАНОВЛЕНО НА СЕРВЕРЕ**. Повторный отказ навигации или подтверждённое повреждение файлов точной опубликованной сборки запускает совместимое восстановление. При сбое сети Release Guard оставляет развёртывание в состоянии, которое удалось подтвердить. Откат разрешён для пар 1.5.209 → 1.5.208 и 1.5.210 → 1.5.209 после синтетического обратного перехода в обоих движках. Восстанавливаются файлы приложения, локальные данные остаются на устройстве.

Архив кандидата и резервный архив предыдущего выпуска хранятся 30 дней. По истечении срока необходим новый проверенный архив, собранный от фактически работающего выпуска. Точная версия кода также остаётся доступна в истории Git.

## Устойчивость и скорость выпуска

- После закрытия или объединения PR его устаревший прогон отменяется; CI точного SHA основной ветки не отменяется этим событием. Все 21 обязательная проверка нового релиза сохранены. Предварительный CI открытого PR и проверка итогового SHA не считаются взаимозаменяемыми.
- Архив Pages имеет уникальное имя для каждой попытки. Перед deploy-pages проверяются регистрация в текущем запуске, точный ID, имя, отсутствие просрочки и ненулевой размер. Ожидание API ограничено; отсутствие подтверждения блокирует публикацию.
- Отдельный Release Guard retry может повторить только job publish один раз: после подтверждённой ошибки регистрации архива до создания развёртывания. Проверяются владелец, точный SHA main, тип и номер попытки, успешный preflight, единственный ошибочный шаг, журнал ошибки и доступность архива. Другие причины, неоднозначные сбои, ошибки безопасности и повторная неудача требуют диагностики. Повтор не запускает заново Quality checks, но повторно проверяет архив и актуальную базу сайта.
- Измеренный полный CI 1.5.210: 5 мин 26 с с очередью; WebKit tablet 224 с, Chromium tablet 200 с. Ускорение за счёт отмены устаревших задач измеряется на следующих выпусках; гарантии фиксированного времени нет. [Успешный CI](https://github.com/rusai-dev/kniga-skazok/actions/runs/45583675443) · [Успешная повторная публикация](https://github.com/rusai-dev/kniga-skazok/actions/runs/45584538532).
- Изменения в CI и документации не требуют новой версии приложения и сами по себе не публикуются. Каждая новая пара версий для безопасного отката требует отдельного подтверждения совместимости в обоих движках.

## Подтверждение на iPad

Установленное приложение проверяет новую версию при возвращении на передний план, после восстановления связи и периодически, пока оно открыто. Service Worker загружает HTML, `release.json` и основные файлы и проверяет их SHA-256. Открытые сказка и рисунок продолжают работать. Запрос на активацию приходит с главного экрана. Service Worker ждёт подтверждения от всех связанных окон, что редакторы закрыты и сохранения доступны. Если вкладка приостановлена и не отвечает, активация ждёт. Уже загруженная сборка может примениться без сети.

В разделе **Для родителей** отдельно видны версия на сервере, текущая версия HTML и подтверждение от активного Service Worker. Для статуса **Обновлено на iPad** открой приложение с домашнего экрана устройства, вернись из редактора на главный экран и проверь строку **Подтверждено на iPad** с ожидаемой версией и кодом оболочки. Сверь код со значением `SHELL_FINGERPRINT` в проверенном `sw.js`. Подтверждение вычисляется на устройстве и содержит только версию и код оболочки. Приложение не передаёт эту строку, личные данные или детские работы. WebKit в CI проверяет сценарий, аппаратный результат фиксируется отдельно.

Первый переход с опубликованной 1.5.209 может потребовать обычного закрытия запущенного приложения и повторного открытия с домашнего экрана после сохранения. Страница 1.5.209 не поддерживает команду новой активации. Для последующих совместимых версий она вызывается с главного экрана автоматически.

## Приёмка и дефекты

Проверяй существующий профиль приложения на синтетических данных. Сказки, незавершённые работы, выбранные обложки, хэши иллюстраций и прогресс сверяй побайтно. Проверяемая резервная копия должна открываться в отдельном профиле или на отдельном устройстве. Резервная ветка кода сохраняет код приложения. Если iPad недоступен, оставляй аппаратную приёмку открытой.

Каждый исправленный дефект получает тест, воспроизводящий его причину. Перед выпуском проверяй PNG обоих движков. Для известных визуальных изменений фиксируй допустимое изменение по экрану и переходу версий с причиной и кадрами до и после. Превышение допуска блокирует выпуск. Допуски и стабильная основа изменяются вручную и проходят собственную проверку.

Экранные и браузерные проверки используют изолированные профили. Рабочая версия сверяется по HTTP и хэшам; подготовка нового архива читает публичные файлы сайта. Разрешённые настольные эмуляции и аппаратные результаты фиксируются отдельно в `SECTION_ACCEPTANCE.md`.
