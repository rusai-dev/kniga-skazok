# Release Ready — безопасный быстрый выпуск

## Правило
Публикация по команде владельца не запускает разработку с нуля. Сначала готовится неизменяемый кандидат (точный commit SHA и базовый SHA), затем параллельно проходят regression, полный browser-smoke Chromium/WebKit, точный переход с действующей версии в обоих движках и визуальные проверки. Только после их успешного завершения и подтверждения резервной копии/приёмки на устройстве кандидат получает статус READY. Отдельный CI job release-ready подтверждает только технические проверки quality.yml, не заменяет визуальные и аппаратные ворота.

## Команда «Публикуй»
1. Сверить SHA кандидата, SHA main, отсутствие конфликтов и актуальность всех обязательных проверок для этого кандидата. При изменении кода или main кандидат переаттестуется; старые зелёные результаты не переносятся автоматически.
2. Проверить резервную ветку кода и независимую резервную копию работ с iPad, её пригодность к восстановлению, результат аппаратной приёмки. Не выгружать детские работы в GitHub. Не требовать повторного полного теста, если SHA и основания приёмки не изменились.
3. По явному разрешению владельца вывести PR из draft и выполнить обычный merge с expected head SHA. Не использовать force, отключение проверок, обход защит.
4. Проверить публикацию GitHub Pages для точного нового main SHA и доступность release.json, HTML и ресурсов. Публикация в GitHub не равна обновлению на iPad; открытый редактор не должен принудительно перезагружаться.
5. При ошибке остановить выпуск, сохранить предыдущий код и данные. Откат не должен очищать хранилища.

## Целевой SLA (инженерная цель, не измеренный результат)
- Готовый кандидат + разрешение: инициирование merge до 30 секунд при доступности API.
- Фактическое развёртывание Pages зависит от очереди и платформы; мгновенность не гарантируется.
- Upgrade-job отдельно от полного smoke: максимум 5 минут вместе с настройкой, диагностический watchdog 210 секунд, отдельные сроки операций. Ни один тест не должен зависать без сообщения о фазе.
- Не запускать повторные тесты без изменения или доказанного инфраструктурного сбоя. Задержка = диагностировать, а не ослаблять ворота.
